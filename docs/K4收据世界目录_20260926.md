### 1.3 盘查发现的两个真缺口

1. **消费侧不读逐条收据**（本次修）：`classify()` 原来只取
   `art.get("worlds_dir")` + `arm{n}` 猜臂归属，顶层键与收据脱钩。
2. **「已清理」与「不可知」不分**（本次修）：失败臂拿不到世界库时的 note 是

   区分「被清过」与「从没记过」。

## 2. 字段设计

### 2.1 生产侧（逐条收据，live 专属；离线逐字不变）

| 键 | 类型 | 语义 | 本次 |
|---|---|---|---|
| `worlds_dir` | str（绝对路径） | 本次跑的世界目录 | 既有（`:351`） |
| `worlds_dir_exists` | bool | **写该收据那一刻**目录是否在 | 既有（`:352`） |
| `created_at` | str | 目录创建时刻 ISO8601 UTC | 既有（`:353`） |
| `worlds_dir_cleaned` | bool | 目录是否已清理 | **本次提前到写时即落 `False`**（`:359`），main 收口处 `:544-545` 的复核写 False 保留 |

为什么把 `worlds_dir_cleaned` 提前到 `run_paired`：原先只有 `main()` 在收口
后 post-fill，**把 `run_paired` 当库直接调用时收据不带这个键**，消费侧只能靠
「有没有这键」猜清理状态。写收据这一刻目录必在（`worlds_dir_exists=True` 已
同时写入），此刻落 `False` 是实况，不是乐观假设；`main()` 保留的复核写入保证
「正常收口留库」这一最终事实也显式落账。

### 2.2 消费侧（报告新增 `worlds` 段，`scripts/k4_accept_report.py`）

```json
"worlds": {
  "worlds_dir": "<地址>",         "source": "receipt|top_level|unknown|receipt_inconsistent",
  "top_level": "<产物顶层键或 null>",  "exists": true,
  "cleaned": false,               "cleaned_basis": "<为什么这么判>",
  "drift": "",                    "receipt_dirs": [], "receipts_with_worlds_dir": 6,
  "recorded_exists": true,        "recorded_cleaned": false,
  "arms": {"A": {"world_db": "<wd>/arm1/k4.sqlite", "readable": true,
                 "locate": "receipt_job_id", "receipt_job_ids": ["scene-…"]},
           "B": {…}}
}
```

关键口径四条：

1. **地址优先级**：逐条收据 `worlds_dir`（权威）> 产物顶层 `worlds_dir`
   （历史口径）> 不可知。收据与顶层不一致、或收据多址 ⇒ 不用静默择一，
   `drift` 里如实并列（`k4_accept_report.py:112-163`）。
2. **臂—世界库映射**：先按收据 `worlds_dir` 遍历 `arm*/k4.sqlite`、用收据
   `job_id` 只读反查（`locate=receipt_job_id`，**机械证据**）；定位不到（旧收据
   无 `worlds_dir`、无 `job_id`，或库不可读）才退回历史口径
   `arm1=A/arm2=B` 并标 `locate=factory_order_fallback`（`:166-199`）。
3. **`cleaned` 三态**（`:127-143`）：`False` 报告时目录仍在；`True` 地址已记、
   报告时不在；`None` 地址不可知。**「不在」不许说成「仍在」；「不可知」也不许
   冒充「已清理」**。`cleaned_basis` 写明依据是「收据记 `worlds_dir_exists=true`
   后消失」还是「产物记有地址但收据未记 `worlds_dir_exists`，无法细分」。
4. **失败臂 note 分三类**（`:202-216`）：已清理（含地址与依据串）/ 地址不可知 /
   在但该臂库不在——不再混成「缺/已清」。判定本身不变：世界库不可核一律
   `insufficient_evidence`（红线：缺证据绝不判通过、也绝不判诚实失败）。

`pass` 行的 `basis` 增一条（`k4_accept_report.py:381-385`）：

```
产物世界库：<wd>/arm1/k4.sqlite（定位口径=receipt_job_id；worlds_dir=<wd>，
来源=receipt，cleaned=False，报告时目录在=True）
```

——即审计要的「这一臂的产物出自哪个世界目录」，直接落在逐行依据里。
