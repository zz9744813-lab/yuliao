# K2 语义审查收据链：逐策略快照、双席签认与 K4 放行

状态：设计稿，2026-09-27。本文不授权写真库、调用模型、批量改策略状态或放行 Writer。实施前以最新代码和只读库态复核下列接口。

## 1. 要解决的断点

`strategy_reviews` 当前只有 `strategy_id`、`judge_kind`、`reviewer_model`、`verdict`、`created_at` 等字段，没有策略版本、证据集合指纹或晋升审计关联。`strategy_instances.reviewer_version` 可原地更新而无复审时间。因此，“同卡两名模型 PASS，且审查晚于实例创建”不能证明它们看过**当前**证据。现有 `k5_promotion_write.py` 的合成库回归甚至在零条 `strategy_reviews` 时仍能走到 `status=verified`。

本次只读核对时，真库有 8 条 `status=verified / observation_status=replicated / effect_status=untested` 的卡、1 个知识包；24 条旧 `strategy_reviews` 均属 2026-09-23 的 `semantic_card`，判词为 merge/retire/rewrite，PASS 为 0。`promotion_audits` 已有 8 条 `replicated` 和 8 条 `verified` 历史行。**这些是历史事实，不因新增门禁被补写成“当时已有双席批准”。**

`scripts/k4_paired_scenes.py::preflight_world` 当前已对非空 A 臂返回 `semantic_review_unverifiable`，两席旧式 PASS 也不放行。这道临时闸应一直保留到下述收据链及端到端测试通过。

## 2. 不复用现有知识包指纹

`app/knowledge_query.py::_evidence_for` 是 K3 的来源准入单源：按实例状态、段角色、来源登记、类型/用途/文本版本过滤，并以 `(canonical_work_id, span_start, span_end)` 去镜像重。`k5_promotion_write.py::evidence_facts` 又把它收窄到严格布尔 `src_ok=true`、`reviewer_version=k2def-v1` 的证据。新快照必须调用这两个既有判据，不能自造一套来源白名单。

先修两处确定性缺口，才可以宣称“同一快照”：

1. `_evidence_for` 当前取实例 `.all()` 后让**首次遇到**的镜像区间入选，没有固定顺序。给查询或去重前序列加稳定次序（至少按实例 ID），用逆序插入、镜像重复的合成库回归钉住返回的代表行及哈希。
2. 当前只按 `strategy_id` 找实例，没有核对 `strategy_instances.strategy_version == expression_strategies_v2.version`。补版本过滤；遇到同一策略 ID 的错版实例，快照构造应显式拒绝或隔离并报警，不能把旧版实例算进新卡。只读真库目前错配为 0，但这不是未来约束。

`fingerprint_knowledge()` 是**全库**四张知识表指纹，适合 K3 包过期判断，不适合作逐策略的语义评审凭据：它含晋升时必变的 `status/scope`，却不含 `segments.role/integrity/text_clean`。`package_sha256` 也不能代替语义批准。

## 3. 快照算法 `semantic-evidence/v1`

新增一个逐策略的纯计算入口，例如 `app/semantic_review.py::build_snapshot(session, strategy_id, target_scope)`。输入策略 ID、显式版本、K5 本次拟写的 scope 主张及**固定的服务器端来源 policy**；不得让调用方通过 policy 放宽 K3 的硬排除。输出规范化 JSON 的 `content_sha256 = sha256(UTF-8(app.knowledge_query.canonical_json(payload)))`。算法版本、来源常量和值一起入负载；今后更改筛选语义须升算法版本，旧版本不自动获认可。

负载只覆盖一张卡，不扫 1,000 万段全库；所有数组按稳定键排序，空值与布尔类型保持原样：

| 部分 | 必含字段与判据 |
|---|---|
| 策略卡 | `id`、`strategy_key`、`version`、`abstract_operation`、`invariants`、`effect_hypothesis`、`failure_modes`、`source`；正文可在持久化摘要里存哈希，在冻结审查输入里保留原文。`status/observation_status/effect_status` 属可变生命周期，不进入内容哈希。 |
| 范围主张 | K5 计划写入的 `scope_to/scope_ids/scope_basis` 与 `scope_rule_version` 单独取 `scope_claim_sha256`。评审看的是拟准入范围；K5 事务按计划值比，K4 事后按当前卡值比。范围变化必须重审。 |
| 正、反实例 | 本卡本版本的**全部** `strategy_instances`，不只挑获选的正例；按 ID 排序。纳入 ID、版本、状态、`reviewer_version`、work/segment ID、文本版本、span、`evidence_sha256` 以及实际 `evidence_text/observed_content/conditions_observed/effect_ref` 的哈希。新负例、复审标记或实例正文原地变化都使旧票失效。 |
| 对应段 | 每个实例关联段的 ID/work ID、`role`、`seg_version`、原文与有效正文（`text_clean` 优先，否则 `text`）的 SHA256、`integrity` 规范化哈希、经 `source_check.parse_src_ok` 得出的严格三态结果。对拟作正证的区间同时执行 `knowledge.verify_instance_span` 和 `knowledge.evidence_sha256` 核对；失配即拒冻结。 |
| 来源登记 | 关联 `work_sources` 的 work/canonical 根、source_type、text_version、text_sha256、作者/题材、用途与授权字段、元数据核对字段；缺登记显式失败。 |
| 条件与筛选结果 | 本卡本版本 `strategy_conditions` 的完整判据字段；`_evidence_for` 返回的准入 refs、剔除原因，以及 `evidence_facts` 的 `src_ok_ids/reviewed_ids/roots`，均排序后入负载。算法记录 K3 服务端硬排常量与调用 policy 的哈希。 |
| 观察锚 | 最近一条到 `replicated` 的 `promotion_audits.audit_id` 及其 `evidence_ref`；快照不得早于这条审计。它标识本轮观察完成点，但不能代替上面逐字段的当前内容哈希。 |

快照构造须在数据库一致性事务内读完；保存冻结审查输入（至少卡定义、逐条证据区间、反例、来源与拟准入范围）及其 `input_sha256`。两席拿**同一个已冻结输入**，模型调用期间不持有数据库写锁。若当时证据变化，后续晋升/K4 重算哈希会拒绝旧票。仅比较 `created_at` 不足以发现原地改 `reviewer_version`；内容哈希才是主要证明。

同一内容允许重新发起审查：`snapshot_id` 是新审查轮次 ID（UUID 或 `sha256(content_sha256 + round_nonce)`），**不要只用内容哈希当主键**。这样一次 BLOCK/ABSTAIN 后可以在新轮次重新审查同一内容，同时保留旧判词；每轮都必须重新核对当前内容哈希。

## 4. 新表与不可变链

保留旧 `strategy_reviews` 和 `promotion_audits` 的行与语义。优先新增三张表，而不是向旧票的自由文本 `note` 塞哈希：

| 新表 | 最小列与约束 |
|---|---|
| `semantic_review_snapshots` | `snapshot_id` 主键、`schema_version`、`algorithm_version`、`strategy_id`、`strategy_version`、`replicated_audit_id`、`card_sha256`、`evidence_sha256`、`scope_claim_sha256`、`policy_sha256`、`content_sha256`、规范化 `payload_json`、冻结 `review_input_sha256`、UTC `created_at`；同一审查轮次只许插一次。 |
| `semantic_review_votes` | `vote_id` 主键、`snapshot_id` 外键、`judge_kind=semantic_current`、实际执行的 `provider/model` 与调用/运行收据 ID、精确 `PASS/BLOCK/ABSTAIN`、`input_sha256`、响应哈希、UTC `created_at`；同一轮次同一**规范化上游模型身份**最多一票。自由填写的 CLI `--reviewer` 不是模型身份。 |
| `semantic_approval_links` | `link_id`、`strategy_id/version`、`verified_audit_id`、`snapshot_id`、两条 PASS 的 vote ID、`kind=pre_promotion/posthoc_release`、`content_sha256`、UTC `created_at`。`pre_promotion` 只在 status 晋升事务中与审计行同写；`posthoc_release` 是事后、面向未来的独立放行事件，不伪称原晋升已批准。 |

三表用 FK、非空、词表/唯一约束和 `BEFORE UPDATE/DELETE RAISE(ABORT)` 实现 append-only；新脚本的 SQLite 写连接必须显式 `PRAGMA foreign_keys=ON`。旧 `strategy_reviews` 的 24 行既不迁为新票，也不改判词。旧 `promotion_audits` 的触发器和行不变，链接以外键**引用**它，不回填审计正文。缺新表、缺字段、未知算法版本、空模型身份或不合法时间均 fail-closed。

票的可采条件：同一 `snapshot_id`、同一冻结输入哈希、同一策略 ID+版本与范围主张，至少两名不同且可证明独立的上游模型 `PASS`；票时间不得早于快照创建，快照不得早于观察审计。已有同轮 `BLOCK` 或预先列为必审席但未完成时不放行，须另开新轮次并保留全部旧票。模型别名指向同一上游时不能冒充两个席位；mock/夹具只验机制，不是生产 PASS。

## 5. 写事务、K4 预检与恢复

`scripts/k5_promotion_write.py` 的 `evaluate()` 可提前显示“缺快照/缺双席/指纹过期”的 `NO-PROMOTE`，但**权威闸在 `commit_promotion()`**：

1. 显式单卡、`--commit` 和签认身份仍是前置。`BEGIN IMMEDIATE` 后，使用同一写事务所绑定的会话重读策略、全部关联证据和票；重算 `semantic-evidence/v1` 内容哈希与 K5 计划的目标 scope。不得先在独立只读会话判绿，再隔一段时间仅 CAS status。
2. 核快照的 ID/版本、观察锚、内容与范围哈希；核两席不同实际模型、同轮精确 PASS、输入哈希、时间、无有效 BLOCK；核策略仍处于 `replicated` 且当前状态/范围与计划一致。
3. 在**同一事务**里 CAS 更新单张卡、插入一条既有 `promotion_audits` 和一条 `pre_promotion` 链接。任何行数不符、证据漂移、审查缺席、FK/触发器错误均回滚，三处都无半成品。直接调用 `commit_promotion()` 也不能绕过门。

`scripts/k4_paired_scenes.py::preflight_world` 继续先核真实登记世界与非空 A 臂；然后对**当次 `query_knowledge` 返回的每一个 selected 策略**逐个查当前内容哈希、scope 主张和有效 `semantic_approval_links`。只要一张未批准/过期，整体 `ready=False`，列明 ID 和原因，真实 `--live` 在构造 GatewayClient 前退出。只读预检可在同一读事务中完成查询与核票，避免同次读数自相矛盾。

CLI 预检不是唯一入口。`app/scene_runtime/knowledge_v2.py::frozen_package_for_scene` 的**首次**查包/prepare 路径也应核票，把批准 manifest（策略 ID+版本、snapshot/link/vote ID、内容哈希、验证时刻）放进不可变的 Runtime job 请求或版本化包收据。已有 job 的崩溃恢复保留“本场已冻结、不重查”契约，但只复用当初确有可核验 manifest 的包；旧 job/旧包缺 manifest，不得在真实 Writer 模式继续消费非空知识。纯夹具模式需显式标成 fixture，不能静默成为生产豁免。K3 旧包可供调查，不因为 `package_sha256` 存在就当作已批准的 Writer 输入。

## 6. 已 `verified` 的 8 张卡

维持当前 `status=verified` 和旧 append-only 审计的历史原貌，同时把这 8 张卡/现有知识包标为**未获语义放行**；K4 临时闸继续拦 Writer。逐卡冻结**当前**证据与目标范围，给至少两名独立席完整盲审。若 PASS，插入 `kind=posthoc_release` 新链接，指向对应历史 `verified` 审计，并在报告里明确“2026-09-27 事后重新核验，未来可用；原 13:17 晋升当时缺席位收据”。K4 仅在当前哈希仍等于该事后链接时放行。若有 BLOCK/证据或范围变更，保持隔离；需要退役/新版本时走显式版本流程，不原地伪造旧票或删审计。批准后重新查询并冻结新包，旧包不自动追认。

## 7. 实施与验收顺序

1. **先钉负例**：现有 `tests/test_k5_promotion_write.py::test_full_ladder_walk_ends_k3_eligible` 在零票下可升 verified，先改为“零票拒绝且库/审计不变”；保留 `tests/test_k4_registered_world_preflight.py` 已有“两条未绑定 PASS 仍拒”测试。此时 K4/live 暂不松闸。
2. 完成 `_evidence_for` 确定性/版本约束和快照纯函数。合成库测试至少覆盖：逆序插入与镜像去重同哈希；新正例、负例、段正文、`role`、严格 `src_ok`、`reviewer_version`、来源授权、条件、卡定义或 scope 改动均换哈希；只有时间戳变化不改内容哈希；错版/缺来源拒绝。
3. 新表模型与旧 SQLite 库升级测试：`Base.metadata.create_all` 可在已有库**只加新表**，重复初始化幂等；旧 24 票和全部晋升审计逐字保留；三表 UPDATE/DELETE 触发器及 FK 生效。`app/db.py` 目前是 SQLite only，不能把 PostgreSQL 当已支持后端。
4. 审查输入冻结与投票入口：同一轮两席看到同一 `review_input_sha256`；重复模型、别名同源、旧轮次、旧输入、ABSTAIN/BLOCK、缺实际调用收据均拒；新轮次可对同内容复审而不覆盖旧轮次。
5. K5 合成库事务测试：两独立 PASS 才能单卡 verified；判绿后至写事务前换一条证据必回滚；直接函数调用不能绕门；CAS、审计、链接任一写失败三处一起回滚；已有 `observed/replicated` 阶梯回归保持。
6. K4 预检与真实模式零调用测试：非空包混入一张未批卡、旧包、过期内容或无 manifest 均拒；全部批准才可预检通过；恢复 job 不重查但必须有原冻结 manifest。通用 K3 查询/离线 fixture 仍按原契约运行，真实 Writer 入口全受闸。
7. 合入并部署门禁后，逐卡处理历史 8 张卡与知识包。每张留独立审查、批准/驳回和最新哈希对账；不把“8 张卡现为 verified”折算成 8 张已批准。旧 K3/K4 收据保留可读，不回写。

实施文件预计涉及 `app/models.py`、`app/db.py`、新 `app/semantic_review.py`、`app/knowledge_query.py`、`scripts/k5_promotion_write.py`、`scripts/k4_paired_scenes.py`、`app/scene_runtime/knowledge_v2.py` 与各自合成库测试。工作应分成可独立审查的提交；真库只读核查和真实模型复核须与机制测试分开报验。
