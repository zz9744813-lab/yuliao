## 1. OPEN-6（低）—— 硬杀残留的运维可处置性

### 1.1 问题（为什么「低危」但仍要收口）

守卫对「锁被拒」只有一条出口：拒绝信息里给锁路径，让人工核实后清除。而硬杀
（SIGKILL / 断电 / 任务管理器结束 / `taskkill /F`）留下带 pid 的锁有两种形态
（均出自本仓库 `REVIEW_r6_lock_realrace.md` OPEN-6 行 + `app/live_guard.py`
模块 docstring「残留」条目）：

| 形态 | 触发条件 | 后果 | 是否需要人工 |
| --- | --- | --- | --- |
| 一：有限砖化 | 死 pid，但锁文件 mtime 仍在 `CORRUPT_LOCK_GRACE_SECONDS`=15s 宽限内 | 整套件 `pytest_configure` fail-fast、exit 2，持续约 15s；宽限一过守卫自愈接管 | 否（等即可） |
| 二：**永久**砖化 | 锁内 pid 已被系统**复用**给无关进程 | `_pid_looks_live` 永远按「存在」判 → 永不自动自愈 → 无限期拒绝 | **是**（只能人工） |

形态二是**设计上接受**的取舍（`_dead_pid_and_stale` docstring「pid 复用风险」段：
不做进程创建时间二次核验，宁可拦不可猜），本任务**不改这个取舍**，只补「人工
处置得起来」的通路。

### 1.2 收口 (a)：运维处置 runbook = 本文件（固定路径）

守卫拒绝信息里以 `OPS_RUNBOOK_DOC` 指向本文件，`test_open6_dispose_hint_is_pure_text_and_runbook_ships`
断言 `(ROOT / LG.OPS_RUNBOOK_DOC).is_file()`——**文档被删/改名会让门转红**，避免
「拒绝信息指向空气」。

### 1.3 收口 (b)：拒绝信息本身带可复制的 `tasklist` 提示

机械判据：**拒绝文本里出现字面量 `tasklist`**，且 `PID eq <n>`、锁路径、
runbook 路径、清锁命令都按本例实参代入（不是模板占位符）。实现是纯文案函数
`_ops_dispose_hint(held, p)`，两条分支：

- 锁内 `pid` 是 int（含被复用的形态二）：
  ```
   ① 锁内 pid 就是本条消息里 held 的 pid 字段：29828。
   ② 确认该 pid 此刻有没有被占用（Windows 首选，可直接复制）：tasklist /FI "PID eq 29828" /NH
      （POSIX 备选：ps -p 29828 -o pid,cmd）——无输出＝pid 确定不存在＝崩溃残留，等 15s 自愈宽限过后守卫会自愈接管、一般无需手清；有输出但确认不是实跑（如 pid 被复用的无关进程，此时**永不**自动自愈）→ 走 ③。
   ③ 确认无人持锁后人工清除该锁文件再重跑（跨平台，可直接复制）：
      "<sys.executable>" -c "import os;os.remove(r'<锁路径>')"
      删前务必确认 ② 的结果里没有实跑进程——宁可拦，不可猜；只删这一把锁文件，勿用任何递归/批量删除命令。
  ```
- 锁内容不可解析（`corrupt_lock`，无 pid 可核）：② 换成
  `tasklist /FI "IMAGENAME eq python.exe" /NH`（列候选进程人工确认）——按 pid
  过滤的命令在无 pid 时不可复制，给不出假出路。

钉死点（`test_open6_refusal_text_carries_copyable_tasklist_hint`）：

1. `refuse_if_live_running` 拒绝文本含 `tasklist`、`PID eq <真实死 pid>`、锁路径、
   `OPS_RUNBOOK_DOC`、`os.remove`、`15s` 宽限字样；
2. 形态二（用本进程 pid 冒充被复用的无关进程、mtime 已拨过宽限）**仍被拒**，
   且文本含 `PID eq <本进程 pid>` 与「永不」字样；
3. `live_lock`（live 侧 `_acquire_lock` 出口）同样带上述要素；
4. 损坏锁分支含 `tasklist` 与 `IMAGENAME eq python.exe`；
5. 全程锁内容**逐字节未动**（`p.read_text() == "不是json"`）——OPEN-6 是纯文案
   改动，不得顺手变成「提示里说能删就删」。

纯度钉死（`test_open6_dispose_hint_is_pure_text_and_runbook_ships`）：同入参两次
输出一致；把 `LG.os.kill` 打成会抛 `AssertionError` 后调用仍返回文本
（**不查进程表**）；调用前后隔离锁位目录内容一致（**不碰文件系统**）；被引用的
runbook 路径真实存在。

### 1.4 运维处置 runbook（正文，可直接照抄执行）

> 触发条件：任何 `python -m pytest ...` 或 `scripts/*--live` 报出
> `[live/pytest 互斥守卫] … 拒绝 …`（exit 2 / exit 1）。守卫已把下面 ①②③
> 三步连同实参一起打在拒绝信息里，**直接复制即可**，此节是同一内容的可检索副本。

**第 0 步：锁在哪**

- 生产锁位：`F:/agi/language-genome/data/live_run.lock`（协议由
  `app/config.py::prod_lock_path()` 单点导出；默认即仓库 `data/`）。
- 排查以**拒绝信息里打印的锁路径**为准——测试进程与 live 进程的锁位可能不同
  （`LG_LOCK_DIR` 旋钮），别默认就是生产位。

**第 ① 步：看锁内 pid**

- 锁内容是 JSON `{"purpose","pid","started_at"}`，`pid` 就在**拒绝信息里
  `held` 字段的那一行**（例：`{'purpose': 'pytest', 'pid': 29828, 'started_at': …}`），
  不必再开文件。
- 需要单独读盘时（如需事后复盘）：

  ```bash
  F:/Hermes/hermes-agent/venv/Scripts/python.exe -c "import json,pathlib;print(json.loads(pathlib.Path(r'F:/agi/language-genome/data/live_run.lock').read_text(encoding='utf-8')))"
  ```

- 若打印出来是 `{'corrupt_lock': True, …}` ⇒ 内容不可解析、**无 pid 可核**，
  直接走第 ③ 步（守卫不会按「死 pid」自愈这类锁）。

**第 ② 步：确认该 pid 是不是真的没人了**

Windows（首选）：

```bash
tasklist /FI "PID eq 29828" /NH
```

- **无输出**（本机实测：只回一行「信息: 没有运行的任务匹配指定标准。」）⇒
  pid **确定不存在** = 崩溃残留。**这时通常什么都不用做**：等锁文件 mtime 超
  `CORRUPT_LOCK_GRACE_SECONDS`=15s 后，守卫下一次进入会记 warning 并自愈接管
  （形态一，15s 内会自愈）。
- **有输出** ⇒ pid 被复用了（形态二）或者**真的有人在跑**。必须看 `IMAGENAME`
  这一列：只有确认它**不是** live 实跑、也不是 pytest 轮，才允许走第 ③ 步。
  若它就是实跑 ⇒ 什么都别动，等对方结束（守卫会自己释放）。
- POSIX 备选：`ps -p 29828 -o pid,cmd`（等价语义）。

**第 ③ 步：确认无实跑后安全清锁**

```bash
F:/Hermes/hermes-agent/venv/Scripts/python.exe -c "import os;os.remove(r'F:/agi/language-genome/data/live_run.lock')"
```

- 跨平台可复制（不依赖 cmd / POSIX 的删除命令差异）。
- 纪律：① 删**这一把锁文件**，路径从拒绝信息里逐字复制；② 删前必须完成 ② 的
  核查；③ 删完直接重跑被拒的命令即可，守卫会用 O_EXCL 原子重建自己的锁。
  **宁可拦，不可猜** —— 拿不准就不要删，回去看 ② 的 `IMAGENAME`。

**已知的两种误读（别照着删）**

1. 看到 exit 2 就删锁 —— 形态一 15s 后自愈，删了只是把「守卫在管」换成
   「没人管」，反而丢掉了自愈与 warning 记录。
2. 看到 `tasklist` 有输出就删 —— 那是 pid **存在**；存在就可能是真持有者
   （`pid` 分支 + `purpose` 比对是 `_release_lock` 保守释放的唯一防线，删错会把
   互斥无声破坏）。

## 2. OPEN-7（低）—— POSIX 分支（`ProcessLookupError` 判死）平台无关覆盖

### 2.1 选择收口判据的哪一条

审查给了二选一：①在 POSIX 上重跑报告 §3 的 (a)(b)(c1)(c2) 四条；②加一条

**本任务取 ②**：本工作目录所在环境只有 win32 一台可跑，① 做不到
（见 §4「未自跑」清单）。② 的关键在于**不许敷衍**——判据明文禁止
`pytest.mark.skipif(sys.platform=="win32")`。新加的两条用例**没有任何
skipif、没有 platform 条件分支**，在 win32 上真跑。

### 2.2 用例 1：`test_open7_posix_processlookuperror_dead_path_parity_with_win32`

伪造进程表的**各种表现**，断言判定口径在 POSIX 与 win32 表现之间**同结论**
（用例不依赖本机真实进程表，故两个平台跑出同一结论）：

| 伪造的 `os.kill(pid, 0)` 表现 | 平台来源 | 期望 `_pid_looks_live` | 期望 `_dead_pid_and_stale` |
| --- | --- | --- | --- |
| 抛 `ProcessLookupError(errno.ESRCH, …)` | **POSIX** | `False`（确定不存在） | `True`（可自愈残留） |
| 抛 `OSError(errno.EINVAL, …)` | win32 | `False` | `True` |
| 抛 `OSError` 且 `winerror = 87` | win32 | `False` | `True` |
| 无异常返回 | 两平台（pid 活着） | `True` | `False` |
| 抛 `OSError(errno.EACCES, …)` | 两平台（受保护） | `True` | `False` |
| 抛 `OverflowError` | 两平台（pid 超长） | `True` | `False` |

### 2.3 用例 2：`test_open7_posix_dead_pid_lock_end_to_end_same_as_win32`

POSIX 判死口径下走**整条守卫链路**，与 win32 口径逐项一致：

1. `refuse_if_live_running` **放行**（不再 brick 套件）并记「死 pid」warning；
2. `whole_run_lock` 以 O_EXCL 接管重建，锁内 pid 变成我方 pid；退出后锁位无残留；
3. 对照组（`os.kill` 无异常＝pid 还活着）：同一把锁 `refuse` 与 `live_lock`
   **仍被拦**，且锁内容里的 pid 逐字未变（不接管、不删）。
