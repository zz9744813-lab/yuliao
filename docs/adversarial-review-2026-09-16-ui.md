## 一、审查方法

1. **盲评不变量逐条验**：A/B → human/candidate 翻译在所有路径（首次判定 / 改判 /
   服务端重端 / 映射丢失）下必须与 `human_was_a` 自洽。
2. **状态机穷举**：review_item × {pending, done, skipped} × 映射 {在, 丢} ×
   winner {A, B, tie, both_bad, cant_judge} 的组合，哪种能写出脏数据。
3. **前端竞态**：连点、连按、跳过中交卷、改判中取题、触屏与鼠标合成事件重复。
4. **测试锚点**：`test_marking_js.py` 按首现标记行切片提取 JS 块，块须自洽；
   全部被钉 ID 须保留。
5. **线上冒烟**：真实库（s30 已判满 / nq50 全待判）跑新端点。

## 三、我审过但判定为**不是问题**的

- **改判会不会污染统计？** 改判只覆盖 `human_verdict` 并记 `rejudged:true` +
  `prev_winner_resolved` + `n_verdicts`；下游统计（judge_matrix / κ）按状态取最新值，
  且 `rejudged` 可供事后剔除。批次计数（`batch_info`）按 `status=done` 计，改判不改变
  状态，不会把 30/30 变成 31/30。
- **serve 端点会不会解盲？** `prev.winner_side` 是相对**本次重洗后** A/B 的位置，
  与本次题面文本同源；用户学到的是「我原判的语义侧现在在哪边」，不暴露哪边是人类。
  前提是重洗随机不可预测——`random.random()` 每次请求重抽，足够。
- **FIFO 逐出风险**：上限 512 远超任何单批同时开题数；真被逐出的题后续判定走
  mapping_lost 分支，降级不静默。
- **非 batch 的 review_next 轮换行为变了**：旧实现无 batch 时永远出最高优先级，
  现在也整批轮换。前端永远带 batch，且轮换对「只浏览不判定」更公平。测试无断言依赖旧行为。

## 四、残留风险（明确不修，理由如下）

1. **P0 令牌泄漏**（9/16 审查已报）：`data/_dbg/serve_out.txt` 与 uvicorn 日志明文存
   令牌，外网 IP 171.107.144.243 仍在探测（重启后日志可见 `401 Unauthorized`，门在工作）。
   轮换令牌 + 扫日志需集霸确认窗口期，本次未动。
2. **改判不留审计快照**：只存最新判定 + 上一判语义。要完整审计链需新表，超出
   「优化 UI」范围。
3. **sessionHistory 仅存内存**：刷新页面后「↩ 改判上一题」失效，需从「已判」列表走
   服务端重端（功能等价，A/B 会重洗）。设计如此，非 bug。
