## OPEN-1（中）——跨进程同 purpose 的保守释放：pid 回读分支入册

**用例**：`tests/test_live_guard_mutex.py::test_open1_crossproc_same_purpose_release_keeps_successor_lock`

**机制**：两个**真实子进程** PY1/PY2 用**同一 purpose**（`t-relay`）交棒：
PY1 取锁就绪 → 父进程 `lockf.unlink()`（模拟人工清锁/崩溃残留自愈）→ PY2 O_EXCL
接管持锁 → 放行 PY1（PY1 迟到退出走 `_release_lock`）。前任回读到的锁 purpose 与
自己**相同**，purpose 比对恒真——拦住它误删继任者锁的**只剩 pid 分支**。在册两条
「保守释放」用例（`test_release_only_deletes_own_lock`、
`test_release_lock_conservative_after_takeover_not_regression`）前任/继任同进程且
purpose 不同，删掉 pid 校验也全绿——这正是审查判定的承重墙缺口。

**断言**：PY1 退出后 ①锁文件仍存在；②内容 `pid == PY2.pid` 且 purpose 仍 `t-relay`
（继任者的锁没被前任删掉、逐字段未动）；③放行 PY2 正常退出后锁无残留；
④`pid1 != pid2`（确为两进程）。子进程就绪/接管用 ready 文件握手 + `_wait_until`
（回调传 lambda，方向 B 的历史误判教训）。

## OPEN-3（中）——LG_DATA_DIR 分叉硬拦（选 (a)：改产品代码）

**选择 (a)**：在 `app/live_guard.py` 的 live 取锁入口加「口径分叉」硬拦（审查实验 e

**产品实现**：`_lock_scope_divergence()`——四条件全真才拦（任一不真即放行，不过拦）：
①本进程不是 pytest（`"pytest"/"_pytest" not in sys.modules`——conftest 覆写

## 产品行为变更（选 (a) 的单列节）

- **变更点**：`live_lock` 进入时新增分叉硬拦（四条件见 OPEN-3）。此前
  「`LG_DATA_DIR` 改而 `LG_LOCK_DIR` 未设」的 live 进程会**静默**在分叉锁位起跑
  （与 pytest/其他同口径 live 互不可见）；现在会被拒绝并给出三选一处置指引。
- **对既有部署的影响**：
  1. **默认口径零影响**：生产跑法不设 `LG_DATA_DIR`（或恰指 `ROOT/data`）＝条件
     ②/④不真，行为逐字节如旧；
  2. **既有用 `LG_DATA_DIR`＋`LG_LOCK_DIR` 双变量的隔离跑法零影响**（协议测试子进程
     即此类，条件③放行）；
  3. **只设 `LG_DATA_DIR` 单变量的既有跑法**（例如整库镜像沙箱）从「静默分叉起跑」
     变为「拒绝＋指引」——需按指引补设 `LG_LOCK_DIR`（要恢复互斥指生产位，要独立
     沙箱指自己目录）。属**收紧**，与守卫既有纪律「宁可拦，不可猜」同向；runbook /
     调度脚本若依赖单变量跑法需同步补一行。
  4. pytest 侧（conftest `whole_run_lock`/`refuse_if_live_running`）不受该判据作用
     （条件①豁免），既有「检查通过后持锁」路径与 25 条在册用例预期行为零变化。
- 模块 docstring 的「残留窄窗 2」已按新口径改写：隐性分叉→声明式隔离才放行。

## 主控亲修与实跑证据（2026-09-26 11:0x–11:5x，主控本人执行，非转述）

**worker 侧的「未自跑」是真实的会话级权限限制**（原文：`Error: Allow Bash to run:
F:/Hermes/hermes-agent/venv/Scripts/python.exe -m pytest ...`）——交付物**首版因此带
三处真缺陷**（作者跑不了门，就没发现）。主控接手亲跑后逐条定位并修复，全部实跑
证据如下（命令与原文，均主控本人执行）：

### 缺陷 1（致命）：OPEN-2 持锁窗挂错位置 ⇒ 主用例必红

- 首版把持锁窗写成 `tests/test_live_guard_mutex.py` 里的
  `pytest_runtest_call` hookwrapper。**pytest 9.1.1 不注册测试模块里定义的
  `pytest_*` 钩子**（只收 conftest.py 与已注册插件）——实测：子 pytest 进程
  跑完即退、整轮锁已释放，父用例 `lock_file.read_bytes()` 直接
  `FileNotFoundError: .../test_open2_real_pytest_process0/live_run.lock`。
- 另：`pytest_runtest_call` 的 post-yield 也不是合适的跨进程窗口。
- **修法（主控亲修）**：窗下移到 `tests/conftest.py::pytest_runtest_makereport`
  包装器——`call` 阶段报告产出后、teardown/sessionfinish（释放锁处）之前阻塞。
  已在 conftest 内写清「为何不能在测试模块」的注释。

### 缺陷 2：pid 断言恒假（venv shim）

- 首版断言 `info["pid"] == holder.pid`（`Popen` 返回的 pid）。**venv 的
  `python.exe` 是 shim**，`Popen.pid` 是 shim 的 pid，shim 再起真解释器 ⇒ 二者
  不等。实测：`Popen.pid=39748 / 子进程 os.getpid()=7228`。
- **修法**：探针把**真实解释器 pid** 写进 passed 标记，父用例读它比对锁内 pid。

### 缺陷 3：失败路径不收尸 ⇒ 持锁子进程活到 120s 兜底

- 首版 `finally` 只在正常路径 `communicate()`；断言失败时子 pytest 不被杀，活到
  120s 兜底超时，既拖长整轮门、又让**下一轮**撞「live/pytest 互斥」假红（实测出现：
  `Exit: [live/pytest 互斥守卫] live 实跑进行中（{'purpose': 'pytest', 'pid': 23148...}）
  ——拒绝 全量 pytest`）。
- **修法**：`finally` 里无条件兜底 `kill()`；另给 `_wait_until` 超时路径加子进程
  输出回贴（首版该路径静默吞掉子进程 stdout/stderr，真红因全在被吞的输出里）。
