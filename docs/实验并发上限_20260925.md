def _pool_plan(exp, models=None) -> dict:
    requested = max(1, int(exp.config.get("concurrency", 4)))
    workers, clamped_from = requested, None
    if requested > limits.MAX_CONCURRENCY:          # ① 上限：与 HTTP 闸同源

## 3. 口径选择与理由

**① 执行侧越界：截断 + 显式记账（`concurrency_clamped_from`），不抛异常。**
理由：
- HTTP 入参侧（`ExperimentIn`）已经拒绝 >16，越界的 config 只可能来自旁路脚本
  或历史落库的实验。那里的 `concurrency=64` 是**既存事实**不是新攻击；
  在 stage 执行中途抛异常会把整条 job 打成 failed，把已经花掉的调用一并废掉，
  还让旧实验永远跑不动 —— 这是把护栏变成可用性事故。
- 截断仍然把并发钉在 16（护栏目的：挡费用放大 / 撞网关限速），达成；
  "静默降级"的坏处是没人知道，故 `concurrency_clamped_from` 进返回结构 +
  一行 stdout 日志，两处都可查。
- 与既有纪律不冲突：`test_server_caps.py:163` 的"越界必拒、不 clamp"钉的是
  **入参契约**；`test_experiment_concurrency_cap.py::test_http_entry_still_rejects_instead_of_clamping`
  显式确认入参侧依旧 422（`concurrency=16` 放行、`17`/`64` 拒）。
  两侧口径不同是刻意的：**入口校验直拒，运行护栏截断并记账**。

**② 串行判定：整段强制 workers=1（最保守），不做并发组/串行组两段式。**
理由：`split_models()` 后先跑并发组再跑串行组要改 stage 的执行结构（幂等键、
计数、stats 语义全跟着动），超出"补闸"范围；且把串行模型混进重建/判定池本身
就是排班错误。代价是混合池会整体变慢 —— 由 `serial_models` 命中名单可见、可查。
`gateway.is_serial_model` 是唯一口径源；若将来要两段式，改 `_pool_plan` 一处即可。

**③ 上限取 16 不动**：与 `api.py:179-180` 既有说明同源（全部实验取值 4、
网关单次超时 300s、4× 余量），本次只解决"执行侧不认这个数"，不重新定价。
