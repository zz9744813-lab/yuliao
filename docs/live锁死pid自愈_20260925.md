## 1. 本轮真实事故原文（2026-09-25 11:40）

主控在仓库跑 `python -m pytest tests/ -q`，被守卫拒绝，输出原文：

```
[live/pytest 互斥守卫] live 实跑进行中（{'purpose': 'pytest', 'pid': 29828, 'started_at': '2026-09-25T10:57:05'}）——拒绝 全量 pytest
```

而 `pid 29828` 早已不存在（`powershell Get-Process -Id 29828` 返回 no such pid）。
锁文件 `data/live_run.lock` 留在盘上 44 分钟（10:57 写入 → 11:40 被拒时仍在），
把整个测试套件 brick 掉，只能人工删锁。主控删锁后全量 pytest 立刻恢复
（1142 passed）。

事故形态总结：**内容合法（purpose/pid/started_at 齐全）+ 死 pid** 的锁，
恰好落在既有两条自愈路径都覆盖不到的死角：

1. `_corrupt_and_stale()`（损坏锁路径）只在**内容不可解析**（`corrupt_lock`）
   且 mtime 超 `CORRUPT_LOCK_GRACE_SECONDS=15s` 时判定为崩溃残留；
2. `refuse_if_live_running()` 与 `_acquire_lock()` 对**能解析**的锁一律按
   「有人持有」硬拦——pid 是否还活着完全不看。

而 `_release_lock()`（含 atexit 兜底）只在**进程还活着**时执行；进程被
SIGKILL/断电/任务管理器结束/`taskkill /F` 硬杀时，锁必然留下且无人可拦、
无人可清。

## 2. 独立复现（修复前 = brick；修复后 = 自愈）

复现手段：在**隔离临时锁位**手工写一把内容合法的锁，pid 填一个
「确定不存在」的 pid，然后调 `refuse_if_live_running(...)` 与
`with live_lock(...)`。确定不存在的 pid 的取法：`python -c` 起一个
helper 子进程，它再起一个短命孙进程后把孙 pid 打印出来，孙进程退出、
helper 也退出（所有进程句柄随之关闭、孙进程对象销毁、pid 从进程表释放，
Windows 上句柄不关则 pid 会“赖着不释放”——已在复现注释里写明），再用
`os.kill(pid, 0)` 实证其确实不在进程表（死 pid 才返回）。

没有任何代码/测试触碰真实生产锁位 `F:/agi/language-genome/data/live_run.lock`。

## 3. pid 存活判定实现

纯标准库 `os.kill(pid, 0)`（零号信号不发信号，只查进程表；POSIX 与
Windows 均支持）——**不新增 psutil 依赖**（psutil 虽在环境可用，但标准库
一层即可完成本机进程表存在性核验，语义也更窄更稳，不引入额外依赖面）。

判定（`app/live_guard.py::_pid_looks_live`），只把**确定不存在**的 pid 判
为死亡，其余一律判「存在」：

| pid 状态 | os.kill(pid, 0) 表现 | 判定 |
|---|---|---|
| 进程存活 | 返回（无异常） | 存在 → 拦 |
| POSIX 查无进程 | `ProcessLookupError` | 确定不存在 → 死 pid |
| Windows 死 pid（表外/已回收） | `OSError` errno=EINVAL(22)/winerror=87 | 确定不存在 → 死 pid（实测本机死 pid 与越界 pid 均此表现） |
| 存在但受保护（如 SYSTEM 进程） | `PermissionError`/EACCES/`SystemError` | 存在/不可知 → 拦 |
| pid 超 32 位不可转译 | `OverflowError` | 不可查 → 拦 |
| 查询函数本体意外抛错 | 任意异常 | 按存在拦，**不删锁** |

Windows 细节（本机 python 3.11.16 实测钉死）：`os.kill(pid, 0)` 内部走
`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`——不存在的 pid 得到
ERROR_INVALID_PARAMETER(87)、映射为 `OSError(22, EINVAL)` 而非
`ProcessLookupError`；存在但受保护得到 ERROR_ACCESS_DENIED(5)。故死 pid
判定必须同时认 `ProcessLookupError` 与「EINVAL / winerror 87」两种表现，
而把 ACCESS_DENIED 类一律当「存在」拦。

## 4. 防误判条件（二选一）与选择理由

任务给的候选：
- (a) `started_at` 距现在超过一个宽限；
- (b) pid 不存在即判定（理由：pid 不存在就不可能有持有者）。

**选定：死 pid（条件一，取 (b) 的核验）+ 锁文件 mtime 超自愈宽限
（条件二，取 (a) 的时间宽限精神，落点用 mtime 而非 started_at）**，与损坏
锁超宽限 `CORRUPT_LOCK_GRACE_SECONDS=15s` **完全同口径**。理由逐条：

1. **pid 存在性核验是比 mtime 猜更强的一级证据**：损坏锁没有 pid 可核，
   只能靠 mtime 猜「建文件后被杀」；合法 JSON 锁有 pid，直接查进程表——
   若 pid 确定不存在，同机当下就不可能有活持有者，这比任何时间宽限都更
   接近「事实」。此即 (b) 的理由，采纳为**必要但不充分**的第一条件。
2. **为什么仍要宽限（必要条件之二）**：与损坏锁的既有口径对称——新落盘
   的锁文件（mtime 在 15s 宽限内）一律按「存在」拦，宁可拦不可猜。若取消
   宽限，一把刚写完的锁会在下一位进入者眼里瞬间变「可接管」，与
   「宽限内可能有进程正在写/正在接管」的既有语义冲突，也让损坏锁与死 pid
   锁的处置出现两条不同的时间线。
3. **为什么取 mtime 而非 started_at**：`started_at` 是写入方**自报**的时间
   戳，可随意编造（锁内写远古/未来时间都能骗过 (a)），还依赖解析；mtime
   是**文件系统事实**，与损坏锁路径的取证来源完全一致，行为同构。既有的
   `test_live_blocks_while_pytest_lock_held` 手工锁（pid 999999999）也是
   「内容合法 + 死 pid」，mtime 口径下因其新落盘而在宽限内被拦，语义保持
   稳定（与「宽限内宁拦不可猜」一致）。
4. 结果：**三相合一才自愈**——「内容合法（可解析 JSON）」「pid 确定不存在」
   「mtime 超 `CORRUPT_LOCK_GRACE_SECONDS`」。缺一即拦，绝不把「看着像残留」
   当成残留。

## 5. pid 复用风险与取舍

- **pid 被系统复用给无关进程**：死 pid 判定查询到「存在」→ 偏「有人持有」
  硬拦、**不删**。只会更保守地拦，绝无「误删活锁」。取舍：接受（宁可拦，
  不可猜）。
- **「pid 存在但不是我方进程」是否额外核验**（如按进程创建时间早于
  `started_at` 反推锁早于进程）：**不做**。理由：进程创建时间戳依赖额外系
  统接口且各有精度/时区/时钟漂移问题，判错方向会引入新的误删面；「宁可拦
  不可猜」，拦住只是保守，猜错则是互斥破口。
- **宽限窗口内的死 pid 锁**：仍拦 15s（与损坏锁一致）。硬杀后 15s 内系统
  仍持「存在」口径，15s 后自动自愈——对事故场景（残余 44 分钟）影响为零，
  对「刚写完就死」的锁只多等 15s，换来与损坏锁完全同构、可预期的行为。

## 6. 哪些情况仍不自愈（明确声明）

- **pid 查询失败 / 权限不足 / 平台无法核验**：一律按「存在」**不删**锁、
  **不**自愈——`os.kill` 抛非确定性异常（含 `OverflowError`、`PermissionError`
  等）即按存在拦，锁连文件都不许删（有测试钉死）。
- **pid 仍存在**（含被复用给无关进程）：按「有人持有」拦，不自愈。
- **锁文件 mtime 在宽限内**：按「存在」拦，不自愈（宁可拦，不可猜）。
- **锁内容无 pid / pid 不是 int**（不可核验）：交给既有「存在」口径拦，
  不自愈（有测试钉死：pid 写成字符串也拦、不删）。
- **损坏锁（不可解析）**：既有口径不变——宽限内拦、超宽限自愈，不因本次
  改动改变。
- **跨机器共享锁位**：进程表是**单机语义**。死 pid 判定假设「锁持有者与
  本进程同机、看同一份本地进程表」；本守卫的互斥协议本来就是 R6 的
  「同机禁止并发窗」语义，默认生产锁位 `repo/data/live_run.lock` 即单机目录。
  若把锁位放到跨机共享目录，别机活进程的锁在本机 pid 必然查不到——会被
  误判为死 pid 并自愈接管，两机互斥退化为「后接管者胜」。**跨机互斥不在本
  守卫支持面内**，跨机应使用分布式锁语义；单机场景下本判定无此误判面。
  （若日后需要支持跨机，需要把 pid 判定收进「同机证据」（如写入 hostname 标记）
  再开，本次明确不做。）
- **人工正在处理的锁**：自愈接管是「unlink + O_EXCL 重建」原子两步，若人工
  恰在同一毫秒删锁/建锁，由 O_EXCL 原子语义兜底，不会出现双持。
