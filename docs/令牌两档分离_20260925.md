## 3. 改动前后对照

### 3.1 令牌读取协议（改前 → 改后）

| | 改前（单令牌） | 改后（两档） |
|---|---|---|
| 评审档 | `REVIEW_TOKEN` env > `data/review_token.txt` > 自动生成并持久化（chmod 600） | **不变**（既有行为回归钉在 `test_access_gate.py`） |
| 管理档 | —（不存在） | **新增** `ADMIN_TOKEN` env > `data/admin_token.txt` > 自动生成并持久化（chmod 600），与评审档同款协议（`app/access.load_admin_token`） |
| 关闸开关 | `REVIEW_NO_AUTH=1` → 全部免令牌 | `REVIEW_NO_AUTH=1` → **两档同时失效**（语义保持，见 §6） |
| 比较 | `hmac.compare_digest(supplied, _TOKEN)` | `_grade()` 对两档分别 `hmac.compare_digest`（管理档命中优先） |
| 包含关系 | — | 管理档 ⊇ 评审档；评审令牌**不能**过管理端点 |

### 3.2 中间件行为（改前 → 改后）

改前：一道全局中间件，`_ok(t)` 对唯一 `_TOKEN` 判定，通过即放行任意端点。

改后（`app/access.install` 内 `_access_gate`）：

```
q_token = request.query_params.get("t")
if q_token and _grade(q_token) is not None:      # 两档任一有效 → 换 cookie
    → 302 跳回干净 URL + set cookie(值=令牌原文)
grade = _grade(request.cookies.get(COOKIE))      # 每次请求按 cookie 值现算档位
if grade is None: → 401 令牌闸门页
if requires_admin(method, path) and grade != "admin": → 403 PlainText
否则放行
```

关键性质：
- **cookie 携带档位**：cookie 里装的是令牌原文，档位由每次请求对两档做
  `hmac.compare_digest` 现算 ⇒ 评审 cookie **永远不会被自动升级成管理档**。
- **`?t=` 既有行为保持**：一次性换 cookie、跳回干净 URL（含原路径与查询参数），
  手机长期免输不变。
- 换 cookie 阶段对**任何** POST（含 admin 端点）都先 302 截住执行端点——评审令牌
  打到 `import-file?t=…` 得到 302 而非 200/500，端点不执行；随后 cookie 请求 403。

## 4. 兼容期开关（仅一条，且必须显式）

**`LG_ADMIN_LEGACY_SHARED=1`**（默认关，字面 "1" 才开，与 `LG_LOCAL_BYPASS` 同口径）：

- 语义：当**未显式配置** `ADMIN_TOKEN`（env 与 `data/admin_token.txt` 都没有）时，
  管理档**共用评审档令牌**——即 `load_admin_token()` 返回评审令牌值
  （`_ADMIN_TOKEN == _TOKEN`，`_grade` 判 admin）。旧单令牌部署迁移期，
  只持旧令牌的人仍能进管理端点。
- **不是静默回退**：任何「没配 ADMIN_TOKEN 就默认可退用 REVIEW_TOKEN」的隐式行为
  一律没有；关掉开关即恢复两档分离（`test_legacy_off_never_returns_review_token`）。
- 启动自检 `self_check()` 在开关打开时**响亮打印**「⚠⚠ 兼容期显式开关：
  LG_ADMIN_LEGACY_SHARED=1 …迁移完成后请去掉」。
- 开关生效后管理档与评审档值相等，cookie 判档命中 admin。

理由：live 侧是既有单令牌部署（`data/review_token.txt` + 浏览器里的老 cookie）。
直接两档分离会让运维者立刻失去导入/建实验的能力，属于可预见的迁移颠簸；
但丢弃「评审=管理」的这台老语义属于审计点名要解决的洞，**不能默认保留**，
故做成必须显式、运行时可见的开关，迁移完成即关。

## 6. 残余风险声明（如实）

1. **持有管理档令牌者仍可导入根内文件**：本次收口只拆「评审 vs 管理」的权限面，
   不新增对管理员的路径约束——管理档令牌导入的仍是「`data/`、`inbox/` 内 + 扩展名
   白名单 + 32 MiB 上限」的文件（路径面由 `app/corpus.py` `_guard_import_path` 负责，
   零改动）。管理员被默认为可信主体，`LG_IMPORT_ROOTS` 外仍不可能读。
2. **`REVIEW_NO_AUTH=1` 场景**：这是显式关闸（本机开发/测试），开启时**两档同时失效**、
   所有端点免令牌。它**不是**部署形态；文档与 `self_check` 都明确其为「仅限本机开发/测试」。
   若运维误在对外环境开它，等同放弃全部鉴权——既有语义从未承诺兜底。
3. **单机明文令牌文件**：`data/review_token.txt` / `data/admin_token.txt` 是明文落盘
   （chmod 600 尽力而为，Windows 上 chmod 语义弱）。能读这些文件的人即可取得对应档位；
   令牌走 HTTPS 隧道，但明文文件本身是单机信任边界。未引入密钥库/TOTP 等任何外部依赖。
4. **管理端点的 HTTP 层现值 403/401**：本文交付的「阻断」形态是中间件对管理端点
   返回 403（无令牌 401）。没有做管理端点的二次确认（如出库前再验一次密码）。
5. **Cookie 档位由值推导**：cookie 明文存令牌值（既有设计），值对得上哪档就是哪档。
   管理员 cookie 与评审 cookie 是不同值、各带各的档；但任一 cookie 泄露=
   对应档位泄露（延续既有单令牌暴露面）。
