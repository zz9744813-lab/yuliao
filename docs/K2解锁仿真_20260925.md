## 1. 三层闸与场景表

K3 查询层（`app/knowledge_query.query_knowledge`）的固定顺序：

1. **层1 status**：`r.status ∈ eligible_statuses(version)`（v1/v2 当前同为
   `{"verified"}`）且 `observation_status ∈ {observed, replicated}`——不满足者在
   **进管道前**被预筛，报告桶名 `status_not_eligible` / `observation_not_eligible`；
2. **层2 证据**：`_evidence_for` 硬剔 `no_registry` / **`benchmark_source`** /
   `excluded_source_type` / `excluded_use` / `text_version` / `mirror_dedup`，
   `evidence_count = 唯一 (根作品, span) 区间数`；0 区间 → `excluded_no_evidence`
   在进入层3 之前被挡；
3. **层3 scope**：`_scope_matches` → `WORK` 需 `book_id ∈ scope_ids`；
   `AUTHOR`/`GENRE` 走登记表反查；`GLOBAL` → `excluded_scope_global_reserved`；
   其余（含 `UNCERTAIN`）→ `excluded_scope_uncertain`。

一次实跑确认的**管道顺序语义**（§3.3.1）：层2 证据检查发生在层3 scope 之前，所以
「只有基准证据、没有合格证据」的策略在层1 放开后以 `excluded_no_evidence` 被挡，
**根本走不到 scope 层**——层3 的哨兵角色只对「有合格证据」的策略成立。
