## 2. 旧口径为何乐观：漏算了哪些闸（附行号）

旧 `k3_evidence_preview` 只对 `(work_id, 段 role 是否 benchmark)` 按
`_evidence_for` 的**来源闸**判一次（source_type / license / text_version），
其余什么都不看。K3 真查询 `query_knowledge`（`app/knowledge_query.py`）里，
来源闸只是**五道闸之一**，而且顺序是「status 预筛 → 来源闸 → condition 管道
→ scope 闸 → 去重排序/预算闸」。旧预演漏算清单：

| 漏算的闸 | K3 位置（`app/knowledge_query.py` 行号） | 真库现状 |
|---|---|---|
| **status 闸**（候选预筛）：`status ∈ eligible_statuses(version)` 且 `observation_status ∈ ELIGIBLE_OBSERVATION` | 常量 `ELIGIBLE_STATUS` 行 35、`ELIGIBLE_STATUS_BY_VERSION` 行 45–48、`eligible_statuses()` 行 53–64、`ELIGIBLE_OBSERVATION` 行 74、预筛在 381–384 | 8/8 status=`hypothesis`（verified 才合格）→ **全拒**，`considered=0` 即此闸所致 |
| **scope 闸**：`scope != UNCERTAIN`、`scope_ids` 命中 book、AUTHOR/GENRE 走登记反查 | `_scope_matches` 行 291–312（UNCERTAIN 落 `excluded_scope_uncertain` 在行 312；调用在行 396） | 8/8 `scope='UNCERTAIN', scope_ids=[]` → **全拒** |
| **condition 管道**：必需条件 unknown/false 与 bad_when 硬排除 | `_condition_pipeline` 行 315–344（调用在行 391） | 当前 8 条无阻断条件；有也不认 |
| **预算闸**：`candidate_cap`/`context_items` 越界拒与 top-cap 截选 | 行 358–369、427、428 | 查询级聚合闸，非单对可判 |
| **去重与排序**：镜像区间去重、多版本同 key 保高版 | `_evidence_for` mirror_dedup 行 281–284；`excluded_duplicate_lower_version` 行 405–424 | 统计层，预演不复制（宁少猜） |

`would_pass_all==0` 还有一个**机制性根因**要说清：`build_queues` 的抽取池只含
`status ∈ {hypothesis, active}`（`scripts/k2_extract_backfill.py` 行 285），而 K3
的 status 闸只放 `verified`——**抽取池与查询合格集的交集为空**，所以当前口径下
抽取池里任何对都过不了 `would_pass_all`。这不是预演缺陷，正是修复要点：旧口径拿
来源闸数字冒充「K3 可达」，真预演如实给出 0，并把「上游要升格谁、给谁钉 scope」
暴露给决策者。

### 3.1 真判据预演的实现纪律（关键）

新增的 `k3_would_pass(s, strategy, segment, text_version, work_source=...)` 对每对
`(strategy, work, segment)` **只调 K3 真函数**（import 复用，绝不复制常量、
绝不重写主流程判定）：

| 闸 | 调用（全部 `app.knowledge_query` 真身） |
|---|---|
| status 闸 | `strategy.status in KQ.eligible_statuses(strategy.version)` 且 `strategy.observation_status in KQ.ELIGIBLE_OBSERVATION` |
| scope 闸 | `KQ._scope_matches(s, strategy, {"book_id": segment.work_id})` |
| condition 管道 | `KQ._condition_pipeline(s, strategy.id, {})`（预演无 semantic_requirements，空 dict 保守求值） |
| 来源闸 | `_k3_source_gate`：按 `_evidence_for` 单实例块的**同一顺序/同一常量**求 would-be 实例（见下） |

三闸（status/scope/condition）直接走真函数，返回值/理由串与 K3 逐字一致
（`excluded_scope_uncertain`、`excluded_required_*` 等）。`would_pass_all` 是四闸
AND，`reasons` 逐闸分桶（所以一个对可能同时出现在 `status_not_eligible` 与
`excluded_scope_uncertain` 两个桶里）。

### 3.2 如实记下的 K3 侧缺口（按派工纪律，不另写主流程判定）

- **缺口**：K3 侧来源闸 `_evidence_for`（行 234–288）**只对已落库的
  StrategyInstance 求值**；对「抽到但未落库」的 pair 没有「按段 / 按假设实例
  判来源闸」的可复用入口。`_k3_source_gate` 因此按 `_evidence_for` 单实例块
  （行 270–279）**同一顺序、同一常量**（`KQ.DEFAULT_EXCLUDED_SOURCE_TYPES` /
  `KQ.DEFAULT_EXCLUDED_USES` / `KQ.DEFAULT_ALLOWED_TEXT_VERSIONS`，全部 import）在
  预演侧求 would-be 实例，理由串与 `_evidence_for.stripped` 一致
  （`no_registry` → `benchmark_source` → `excluded_source_type:..` → `excluded_use`
  → `text_version:..`）。这段镜像是在本文件模块文档里如实标注的**缺口镜像**，不是
  新增独立判定；它已由测试钉死与 `upper_bound`（旧来源闸判定）逐字同值
  （`would_pass.would_pass_source == would_reach_k3`）。
- **建议**：把 `_evidence_for` 的单实例来源闸块（行 270–279）抽成一个公开的
  `source_gate_for(work_id, segment_id, text_version)` 只读入口，预演直接改调它、
  删掉本镜像。本任务禁改 `app/knowledge_query.py`，故只记录建议不实施。

## 5. 测试用例（`tests/test_k3_preview_reach.py`）

1. `test_true_preview_pins_current_truth_eight_hypothesis_uncertain`：**真库口径
   钉死**——8 条全 hypothesis/UNCERTAIN 时 `would_pass_all==0` 且
   `excluded_scope_uncertain>0`（并断言 8 条 `status not in eligible_statuses`，
   与 K3 根因一致）。这条就是防止以后有人把预演改回乐观口径的钉子。
2. `test_reverse_pin_scope_clear_status_upgraded_passes_and_gates_gate`：**反向钉**——
   scope 明确（WORK+scope_ids 命中）+ status 升格（verified）→ `would_pass_all>0`
   （预演不是恒 0 的死门）；拔掉任一闸（status 降回 hypothesis / scope 改 UNCERTAIN
   / text_version 出允许集）立即归 0 且对应桶出现。
3. `test_would_pass_reports_benchmark_source_gate_at_pair_level`：benchmark 段在
   真判据段同样如实剔除（per-pair `benchmark_source` 桶），旧字段逐字兼容。
4. `test_query_knowledge_consistency_before_and_after_evidence`：与 `query_knowledge`
   一致性——同一策略同书，未落实例时真查询只差在 `excluded_no_evidence`（预演说
   「全过」恰是「只剩证据没落」）；落 verified 实例后真查询直接命中。
5. `test_query_knowledge_consistency_pin_still_empty_after_instances`：hypothesis/
   UNCERTAIN 即便有 verified 实例也不进 selected（status 预筛根因复核）。
6. `test_would_pass_public_api_shape`：`k3_would_pass` 公开 API 形状与四闸布尔。

## 6. 复核与边界

- 预演是**只读**的：不落实例、不改 K3；真判据段对 would-be 实例求值，不因缺实例
  而假装「无证据故不可达」（那不是本预演要回答的问题——回答的是「抽到并核验后
  能不能进 K3 候选」）。
- 预算闸（candidate_cap/context_items）与镜像去重/排序是**查询级聚合**，单对预演
  不复制，以 `query_knowledge` 为准（其 `budget.considered` 自会对刚从候选集算出）。
- 源码复用纪律已由测试钉死：`would_pass.would_pass_source == would_reach_k3`
  （新来源闸镜像与旧来源闸判定同值），`app/knowledge_query.py` 未改一行。
